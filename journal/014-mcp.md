# 014 — Feature 13: MCP tool servers

## Goal

Use tools from any MCP (Model Context Protocol) server, the shared standard
that Claude Code, Hermes Agent and many others support. This is how the harness
gets "connect to any tool", and why tools can be written in any language.

## The big idea

An MCP server is just another program. We start it and exchange **JSON-RPC 2.0**
messages over its stdin/stdout, one JSON object per line:

```
horde ── initialize ──────────────► server
      ◄──────────── capabilities ──
      ── notifications/initialized ►
      ── tools/list ──────────────►
      ◄──── [{name, description, inputSchema}, …]
      ── tools/call {name, arguments} ►
      ◄──── {content: [{type: "text", text}], isError}
```

Each server tool becomes an ordinary `Tool`, so the loop, approval, traces and
truncation all work unchanged. MCP's `inputSchema` is already JSON Schema, so it
goes to the model as-is.

## Decisions

| Question | Choice and why |
|----------|----------------|
| Transport | **stdio** only. It's the most common for local servers and needs no networking. HTTP transport later if needed. |
| Config format | `{"mcpServers": {name: {command, args, env}}}`, the shape other harnesses use, so existing configs can be copied. |
| Where config comes from | **Only `~/.horde/mcp.json` or an explicit `--mcp-config`.** Not auto-loaded from the project folder: a cloned repo must not be able to start programs on your machine. |
| Tool names | `mcp__<server>__<tool>`: no clashes between servers or with built-in tools, and it's clear where a tool comes from. |
| Approval | **Always ask** for MCP tools. They're outside code with unknown side effects. |
| Errors | `isError` results and JSON-RPC errors become `Error: …` text for the model, like any tool failure. |
| Server chatter | Notifications (messages without our id) are skipped while waiting for an answer. |

## What was done

```
src/horde/mcp.py                    new: MCPServer (start, request, tools, call, close), load_mcp_servers
src/horde/cli.py                    --mcp-config; servers' tools added; servers closed at the end
tests/fixtures/fake_mcp_server.py   new: a tiny MCP server (echo, fail) for tests
tests/test_mcp.py                   new: 5 tests
tests/conftest.py                   tests never read the real ~/.horde/mcp.json
```

## How it was tested

`uv run pytest` gives **93 passed** (88 + 5 new), all against a **real subprocess**
speaking MCP: tool listing and names, missing schema handled, approval
required, call through the loop (with a notification in between), `isError`,
JSON-RPC error, missing config, and the full CLI path.

Live (`groq:openai/gpt-oss-120b`): with the fake server configured, "use the
echo tool to repeat 'hello from mcp'" gave an approval prompt for
`mcp__fake__echo`, then `y`, then the tool result, then the correct answer.

## Known gaps

- stdio only (no HTTP/SSE servers); tools only (no MCP resources or prompts).
- No timeout if a server hangs mid-call (Ctrl+C still works).
- If one server fails to start, servers already started aren't closed.

## What you should learn here

- **Protocols beat plugins.** Any program that speaks MCP is a tool, in any language.
- **Adapt at the boundary.** MCP tools become normal `Tool`s, and nothing else changed.
- **Config that runs programs is a security boundary.** Only trust config the user chose.
- **Test against a real process.** The fake server exercises real pipes and JSON framing.
